# 你不知道的 Agent：原理、架构与工程实践

- **作者:** Tw93
- **日期:** 2026-03-21
- **出处:** Tw93

## 概览
这篇文章不是在讲“Agent 很神”，而是在系统拆解：一个能稳定落地的 Agent，到底靠什么工作。作者的核心结论很明确：真正决定效果的，往往不是换更贵的模型，而是外部工程条件——包括 Harness、上下文组织、工具设计、记忆系统、评测方法和安全边界。

如果只盯着模型能力，容易把很多本质上属于系统设计的问题，误判成“模型不够强”。

## 核心判断

### 1. Agent Loop 本身其实很简单，复杂度主要在循环外
Agent 的核心控制流就是：感知 → 决策 → 调工具 → 接收反馈 → 继续下一轮，直到输出最终文本。主循环通常很稳定，新增能力一般通过三种方式接入：
- 扩展工具集和 handler
- 调整系统提示结构
- 把状态外化到文件或数据库

作者的意思很明确：**不要把主循环做成巨大的状态机**。模型负责推理，外部系统负责状态、边界和约束。

### 2. Workflow 和 Agent 的区别，本质是控制权归谁
- **Workflow：** 路径由代码预定义，输入相似时执行路径也固定
- **Agent：** 下一步由 LLM 动态决定，允许中间推理、试错和自修复

不是所有任务都适合 Agent。流程固定、边界明确的事情，Workflow 往往更稳；需要灵活判断和中间推理时，Agent 才更有价值。

### 3. 常见 AI 系统，本质上是五种控制模式的组合
作者把常见设计归纳成五类：
- Prompt Chaining
- Routing
- Parallelization
- Orchestrator-Workers
- Evaluator-Optimizer

重点不是“必须做完整 Agent”，而是**按任务特征选控制模式**。很多场景拼两三种模式就够了。

## 为什么 Harness 比模型更关键

### Harness 决定系统能不能稳定工作
作者把 Harness 理解为 Agent 外围的验证和约束基础设施，至少包括：
- 验收基线
- 执行边界
- 反馈信号
- 回退手段

结论非常实用：**在代码这类高可验证任务里，Harness 往往比模型本身更关键。**

### OpenAI 的实践说明：速度快，不只是因为模型强
文中引用 OpenAI 的 agent-first 开发经验，重点不是“模型多厉害”，而是几个工程决策：
- Agent 看不到的内容，等于不存在，所以知识必须在代码库内可见
- 约束要编码进 linter、类型系统、CI，而不是只写文档
- Agent 要能端到端自主完成验证、修复、提 PR、处理 review
- 高吞吐下，减少人工等待比追求零瑕疵更重要

作者强调：**写代码的纪律没有消失，只是从人工 review 转成了机器可执行约束。**

### 最适合 Agent 的任务，在“目标清晰 + 可自动验证”的象限
如果目标明确、结果又能自动验证，Agent 最容易发挥；
如果任务模糊、验收靠人盯，Agent 很容易高效地朝错误方向跑。

一句话概括：**Harness 的目标，就是把任务尽量推向“清晰且可验证”。**

## 上下文工程为什么决定稳定性

### 1. 很多“模型不行”，其实是 Context Rot
上下文太长、噪声太多，关键信号会被稀释。作者认为，实践里最常见的问题不是窗口不够长，而是**信息密度失控**。

### 2. 上下文应该分层，而不是全塞一起
作者建议至少分成这几层：
- **常驻层：** 身份、硬规则、禁止项
- **按需加载：** Skills、领域知识
- **运行时注入：** 时间、渠道信息、动态偏好
- **记忆层：** MEMORY.md 这类跨会话信息
- **系统层：** Hooks、代码规则、确定性逻辑

核心原则：**确定性逻辑不要放进上下文，能放到系统或工具层就放过去。**

### 3. Prompt Caching 和上下文分层是联动的
缓存命中要求前缀稳定，所以系统提示、工具定义、长文档这些稳定内容适合放前面；动态内容放后面。一个反直觉但很重要的点是：

**稳定的大前缀，长期成本可能低于频繁变化的小提示。**

### 4. Skills 的正确打开方式：常驻索引，正文按需加载
作者非常强调 Skills 的描述要像路由条件，而不是功能广告。真正关键的是：
- 什么时候该用
- 什么时候不要用
- 产出是什么

而且反例非常重要。文章里提到，没有反例时，Skill 路由准确率会明显下降。结论就是：**Skill 描述写不好，路由失败不是模型的锅。**

### 5. 文件系统是很适合 Agent 的上下文接口
相比把大量 JSON 直接塞回上下文，更好的方式通常是：
- 工具把结果写文件
- Agent 再按需 grep / 读取

这样能降低上下文污染，也方便人类调试。这个思路和 Dynamic Context Discovery 很接近。

## 工具设计决定 Agent 能做什么

### 1. 工具质量比工具数量更重要
工具太多不仅占上下文，还会分散模型注意力。文章里一个很实用的判断是：

**大多数工具问题，不是缺工具，而是工具设计视角错了。**

### 2. 工具应该围绕 Agent 的目标设计，而不是围绕 API Endpoint 设计
作者把工具设计分成三代：
- **第一代：** API 封装，粒度细、需要多个工具拼起来
- **第二代：** ACI（Agent-Computer Interface），围绕任务目标定义工具
- **第三代：** Advanced Tool Use，包括动态发现、代码编排、示例驱动

最重要的跃迁是：**从“工具能做什么”转到“Agent 为达成目标需要什么动作”。**

### 3. 好工具应该具备三个特征
- 参数语义清楚，不模糊
- 返回值只保留对下一步决策有用的信息
- 报错结构化，并带修正建议

作者的观点很明确：调试 Agent 时，**先查工具定义**，别先怪模型。

### 4. 工具调用示例很重要
JSON Schema 只能约束参数类型，不能说明“该怎么用”。真实调用示例能显著提升工具调用准确率。

## 记忆系统如何设计

### 1. Agent 没有天然的跨会话连续性
会话一结束，上下文就没了，所以记忆层不是锦上添花，而是基础设施。

### 2. 作者把记忆分成四类
- **工作记忆：** 当前上下文窗口
- **程序性记忆：** Skills，知道“怎么做”
- **情景记忆：** 会话历史，记录“发生了什么”
- **语义记忆：** MEMORY.md，沉淀稳定事实

这套分法的价值在于：不同记忆解决不同问题，别混着存。

### 3. MEMORY.md 和 daily logs 这种 Markdown 方案很实用
文中以 OpenClaw 为例，强调混合检索方案的优点：
- `memory/YYYY-MM-DD.md` 记录原始细节
- `MEMORY.md` 保存精选事实
- `memory_search` 只在需要时检索相关内容

作者的判断是：**大多数 Agent 场景，结构化 Markdown + 检索，已经比很多人一上来就上向量库更实用。**

### 4. 记忆整合必须可回退
整合旧消息时，不应该直接删除原始内容，而是只移动“整合指针”，失败时还能回到原始记录。重点不是摘要多漂亮，而是**流程可恢复、不会丢数据**。

## 如何逐步放开 Agent 自主度

### 1. 长任务不能只靠单个 session 硬撑
作者建议把长任务拆成两个角色：
- **Initializer Agent：** 只负责初始化任务结构、生成文件、建立初始状态
- **Coding Agent：** 每轮只完成一个功能，测试、更新状态、提交后退出

这套设计的重点是：**把任务状态外化到文件系统，而不是留在上下文里。**

### 2. 任务进度要显式写出来
文中建议用结构化文件记录任务状态，例如 pending / in_progress / completed，并要求同一时间只有一个 in_progress。这样 Agent 才不容易偏航或提前误判完成。

### 3. 慢速 I/O 应该后台化
网络请求、长时间文件操作、耗时命令会阻塞主循环。更稳的方式是把慢速 subprocess 放到后台，通过通知队列把结果注入下一轮上下文。

## 多 Agent 如何组织

### 1. 多 Agent 的重点不是“并行”，而是“隔离 + 协作”
作者区分了两种模式：
- **指挥者模式：** 人和单 Agent 紧密同步协作
- **统筹者模式：** 主 Agent 异步委派多个子 Agent，并最终审核产出

真正有价值的地方，不是多开几个模型，而是把中间过程沉淀成可持久化工件，比如分支、PR、日志和任务文件。

### 2. 子 Agent 应该隔离搜索和试错噪声
主 Agent 需要的是结论，不是子任务里的所有搜索过程。因此子 Agent 应有独立上下文，完成后只回摘要。

### 3. 协作必须协议化
多 Agent 之间不能只靠自然语言约定。作者建议明确三样东西：
- 协作协议（如 JSONL inbox）
- 任务图（依赖关系）
- 隔离边界（如 worktree）

顺序也很重要：**先协议、先隔离，再谈协作。**

### 4. 多 Agent 会放大幻觉，需要交叉验证
一个 Agent 的错误可能被其他 Agent 接力强化，所以最终还得依赖测试、独立验证 Agent、编译器或人工审查来打断错误传播链。

## Agent 评测如何做

### 1. Agent 评测比单轮问答复杂很多
单轮问答只要看回答内容；Agent 评测则要同时关注：
- 任务本身
- 运行环境
- 工具调用
- 执行记录 transcript
- 环境最终 outcome
- 评分器和评测 harness

结论是：**不能只看 Agent 说了什么，必须看环境最后真的变成了什么。**

### 2. 两个核心指标不能混用
- **Pass@k：** 跑 k 次至少一次成功，适合看能力上限
- **Pass^k：** 跑 k 次全部成功，适合做上线回归

这点很关键。很多团队把探索性评测和稳定性回归混在一起，最后会误判系统水平。

### 3. 评分器优先级很明确
- 有确定答案：优先代码评分器
- 需要语义判断：再用模型评分器
- 拿不准：用人工标注校准

作者很强调：**能代码判定，就别先上 LLM judge。**

### 4. 先修评测，再改 Agent
这是全文里我觉得最容易被忽略、但特别重要的一条。系统表现下降，不一定是 Agent 退化，也可能是：
- 环境资源不够
- 评分器有 bug
- 测试集和真实场景脱节
- 聚合分数掩盖了局部退化

所以如果评测本身有问题，基于它去改 Agent，很可能越改越偏。

## 我认为最值得记住的几点

### 1. 别把 Agent 问题都归因到模型
很多失败是系统问题：上下文脏了、工具设计差、验收不清、评测坏了。

### 2. 让 Agent 稳定工作的关键，是“外部结构”
包括：
- Harness
- Context 分层
- 好工具
- 文件化状态
- 可恢复记忆
- 严肃评测

### 3. 自主度不是靠“少点确认”获得的
而是靠：
- 跨 session 续跑能力
- 显式进度状态
- 后台 I/O
- 可验证结果
- 回退机制

### 4. 工程上最重要的是把任务变得可验证
只要目标和验收足够清楚，Agent 的效果会稳定很多；否则再强的模型也容易乱跑。

## 一句话总结
这篇文章最核心的价值，不是介绍 Agent 概念，而是把一个常被神化的话题拉回工程现实：**Agent 成败的决定因素，通常不是“模型够不够聪明”，而是你有没有把上下文、工具、记忆、评测和验证体系搭好。**
