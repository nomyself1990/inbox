# Neo Lee：EWD 667、自然语言编程与窄接口

- **来源:** https://digest.soulhacker.me/digest/ewd-667/
- **作者:** Neo Lee
- **日期:** 2026-04-01
- **出处:** 阅读笔记

## 概览
这篇文章是 Neo Lee 对 Dijkstra 经典短文 **EWD 667 — _On the foolishness of “natural language programming”_** 的导读与延伸评论。核心观点很锋利：**编程里最有价值的，不是让机器“更懂人话”，而是把表达压缩成更严格、更窄、更可验证的形式系统。**

如果只记一句话：**自然语言适合提出需求和探索问题，但要让机器可靠执行，中间一定要经过形式化；“会说人话”不是可靠系统的终点，窄接口才是。**

## 文章在讲什么
Neo 先交代了背景：Dijkstra 会把自己的文章、备忘和讲稿编号为 `EWD nnn`，而 `EWD 667` 写于 1978 年前后，标题就叫 **《论“自然语言编程”之蠢》**。这不是在吐槽某个具体产品，而是在批判一种长期反复出现的幻想：

- 问题在于机器太笨、编程语言太僵
- 只要机器更懂自然语言，开发就会更轻松
- 形式化表达只是人为负担，最好能被机器替代

Neo 认为，Dijkstra 的反驳到今天依然成立，而且几乎是在隔空点评当下的 AI 编程热潮。

## Dijkstra 的核心论点
文章把 Dijkstra 的判断归纳得很清楚：**编程语言的形式化不是负担，而是优势。**

软件开发真正难的，不是把一句想法“说出来”，而是把需求表达得足够：

- 没有歧义
- 没有隐藏矛盾
- 能被机械、稳定地执行
- 能被别人检查、推理、证明

而这些恰恰不是自然语言擅长的。自然语言的“自然”，很大程度上来自：

- 依赖上下文
- 允许默认前提
- 容忍模糊表达
- 很容易说出“听起来合理但其实不严谨”的话

Neo 引了 Dijkstra 那句很经典的话：**自然语言最大的“自然性”，恰恰是它让人更容易说出荒谬而不自知的话。**

## 关键概念：窄接口（narrow interface）
这篇导读里最值得记的，是 Neo 把 Dijkstra 的另一个洞察讲透了：

**接口设计不是把同样的工作量在两边重新分配，而是会改变总工作量。**

很多人会觉得：

- 机器更聪明一点
- 多替人理解一点
- 人就能少做一点

但 Dijkstra 的判断相反：接口越宽、越模糊、越依赖解释，跨接口沟通和纠错的成本就越高。真正高效的人机协作，往往依赖 **窄接口**：

- 可表达的东西有限
- 规则少但清晰
- 合法与不合法边界明确

Neo 把这个概念和今天的工程实践连得很自然：

- 编程语言
- 类型系统
- 协议
- API
- 数据库 schema
- JSON Schema
- DSL
- structured output
- function calling

本质上都在做同一件事：**把模糊世界压缩成机器可用的严格接口。**

## 为什么这跟今天的 LLM 特别相关
文章最有现实感的部分，是把 `EWD 667` 映射到今天的 AI 工程。

Neo 的判断很明确：

- “低代码 / 无代码 / 只写 prompt 就能开发软件”
- “AI 取代程序员”
- “自然语言就是新编程语言”

这些说法，本质上都延续了当年“自然语言编程”的同一种冲动：**希望把形式化的负担整体推给机器。**

但现实恰恰在反过来证明 Dijkstra：

- 模型自由说话时，看起来很聪明
- 一旦要接入生产系统，就必须受限于格式、类型、协议
- structured output 一旦不严格，系统马上变脆
- 例如把 `<think>` 或多余文本混入结构化输出，整个调用链就可能崩

Neo 这里点得很准：今天大家热烈讨论的 **harness engineering**，从思想上说，其实就是老派计算机科学里的 **narrow interface**。

## 自然语言的边界
文章并不是说自然语言没用。相反，Neo 也明确写了：自然语言非常适合：

- 提需求
- 探索问题
- 交流直觉
- 描述目标
- 传递动机和灵感

问题不在“能不能用自然语言开始”，而在于：**从“我想要什么”到“机器应如何可靠执行”，必须经过一个形式化过程。**

所以架构师、系统设计师、程序员最核心的能力，并不是记住某门语法，而是：

**把模糊想法压缩成足够严格、足够窄、足够可靠的形式系统。**

## 我觉得最值得记的点

### 1. 这不是反 AI，而是反“把精确性交给奇迹处理”
Neo 不是在说 LLM 没价值，而是在提醒：**LLM 真正有价值的地方，往往要靠更强的约束来托底。**

### 2. “更会说人话”不等于“更适合做接口”
对人好用的表达方式，不一定对系统可靠。系统边界最怕“差不多”。

### 3. AI 工程的关键工作，还是结构化
今天很多所谓 AI 产品竞争，最后拼的不是 prompt 文案，而是：

- 输入怎么约束
- 中间状态怎么建模
- 输出怎么验证
- 错误怎么恢复
- 接口怎么缩窄

### 4. Dijkstra 其实是在定义编程的本质
从这个视角看，编程不是“写代码”，而是**把模糊意图翻译成形式化系统**。这一定义放到 agent / tool calling / workflow automation 时代，反而更贴切了。

### 5. 对当下 AI 热潮是个很好的降温剂
这篇东西的价值，不在于给人泼冷水，而在于提醒：**别把自然语言当终点，把它当入口。真正的工程价值，发生在入口之后的压缩、约束与验证。**

## 一句话总结
**Neo Lee 借 Dijkstra 的 `EWD 667` 讲明白了一件事：可靠的软件系统不是靠“更自然”的语言建成的，而是靠更窄、更明确、更可验证的接口建成的；LLM 时代越热，这个判断越不过时。**
